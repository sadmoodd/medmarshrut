# Отчёт backend-разработчика

**Участник:** Блынских Данил
**Роль:** backend-разработчик (FastAPI, движок диалога, REST API, интеграция с core MAX)

## Что сделано

Серверная часть на **Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2.0**.

Код разделён на слои:

| Слой | Файл | Что делает |
|---|---|---|
| Предметная область | `app/domain/dialog.py` | Порядок вопросов, условия показа, прогресс, проверка ответов, поиск экстренных признаков |
| | `app/domain/triage.py` | Правила: специалист, срочность, место, обоснование |
| | `app/domain/text_analysis.py` | Разбор свободного текста по ключевым словам, удаление телефонов и e-mail |
| | `app/domain/knowledge.py` | Вопросы, варианты, категории (данные, согласованные с аналитиком) |
| Прикладной | `app/services.py` | Сценарии: создать сессию, принять ответ, назад, удалить, автоочистка |
| Транспорт | `app/api.py` | HTTP-эндпоинты, коды ошибок |
| Интеграция | `app/integrations/max_gateway.py` | Клиент core MAX: обмен токена пользователя на профиль |
| Запуск | `app/main.py` | Создание приложения, CORS, заголовки безопасности, фоновая очистка |

Главный принцип: **домен не знает про БД и HTTP**. Функция `evaluate(state)` получает ответы
и возвращает статус (`active` / `emergency` / `completed`), следующий вопрос и прогресс.
Поэтому медицинскую логику легко тестировать и можно подключить к любому каналу.

### Как обрабатывается ответ

1. `POST /api/v1/sessions/{id}/answers` с телом `{step_id, option_ids, text, skip}`.
2. Pydantic проверяет типы и длину (текст ≤ 500 символов, не более 20 вариантов).
3. Проверяется токен из заголовка `X-Session-Token`.
4. `validate_answer` проверяет, что ответ относится к текущему вопросу, варианты существуют,
   «Нет» не совмещён с другими, необязательный вопрос можно пропустить. Из текста удаляются ПДн.
5. Ответ сохраняется, затем `evaluate` **заново проверяет все ответы** на экстренные признаки.
6. При экстренном признаке статус `emergency`, событие пишется в журнал, создаётся экстренная
   рекомендация. Если вопросы кончились — строится карточка `triage_results`.
7. Клиенту возвращается полное состояние: вопрос, прогресс, история, карточка.

Ошибки: 422 — некорректный ответ (с понятным сообщением на русском), 409 — опрос уже
завершён, 403 — неверный токен, 404 — сессия не найдена или истекла, 502 — core MAX недоступен.

### Эндпоинты

`GET /health`, `POST /sessions`, `GET /sessions/{id}`, `POST /sessions/{id}/answers`,
`POST /sessions/{id}/back`, `DELETE /sessions/{id}`, `POST /integrations/max/auth`,
Документация Swagger: `/docs`.

### Вход из MAX

1. Пользователь открывает бота https://max.ru/id6685107786_bot и нажимает кнопку нашего сервиса.
2. Мини-приложение открывает наш URL с параметром `?token=<JWT>`; JWT живёт 5 минут.
3. Фронтенд сразу забирает `token`, стирает его из адресной строки (`history.replaceState`)
   и отправляет на `POST /api/v1/integrations/max/auth`.
4. Бэкенд один раз вызывает core: `GET {CORE_URL}/api/v3/users/user-for-external-service?token=<JWT>`
   с заголовком `Authorization: Bearer <CORE_SERVICE_TOKEN>`. Сервисный токен есть только на сервере.
5. Из профиля берём минимум: `_id` (хранится только как HMAC), возрастную группу (из даты
   рождения) и пол. Имя показывается в приветствии и не сохраняется. СНИЛС, полис ОМС,
   ФИО и телефон отбрасываются сразу и в БД не попадают.
6. Первый вопрос: «Для кого вы ищете помощь?». «Для себя» — возраст и пол подставляются из
   профиля (в истории помечены «из профиля MAX»). «Для другого человека» — бот спрашивает
   их, потому что профиль описывает владельца аккаунта, а помощь может быть нужна ребёнку.
7. Без `token` (страница открыта не из бота) сервис работает анонимно и подсказывает открыть его из бота.

Ошибки core: 401 — ссылка устарела (просим открыть бота заново), 404 — пользователь не найден,
403/5xx/сеть — 502 «Сервис авторизации временно недоступен», с возможностью продолжить без входа.

## Вопросы комиссии

1. **Почему FastAPI, а не Django или Flask?**
   Встроенная валидация через Pydantic, автодокументация OpenAPI, высокая скорость и
   минимум лишнего для API-сервиса. Django избыточен (админка и шаблоны не нужны), во Flask
   валидацию пришлось бы писать вручную.
2. **Как устроен переход между вопросами?**
   Есть упорядоченный список шагов и условия применимости. Следующий вопрос — первый
   применимый шаг без ответа. Уточняющий вопрос строится по выбранной категории.
3. **Как реализована кнопка «Назад»?**
   Удаляется последний ответ (по полю `seq`), рекомендация сбрасывается, состояние
   пересчитывается. Так можно отменить и ошибочный экстренный ответ.
4. **Что если клиент пришлёт ответ не на тот вопрос?**
   Сервер сверяет `step_id` с текущим вопросом и вернёт 422. Пропустить или подменить шаг нельзя.
5. **Где хранится состояние диалога?**
   В БД, в таблице ответов. Сервер ничего не держит в памяти, поэтому можно запустить
   несколько копий и сессия переживёт перезапуск.
6. **Как аутентифицируется пользователь без логина?**
   При создании сессии выдаётся случайный токен (256 бит). Клиент шлёт его в заголовке, в БД
   хранится только хеш. Сравнение идёт за постоянное время (`hmac.compare_digest`).
7. **Почему синхронный SQLAlchemy?**
   Нагрузка MVP небольшая, запросы короткие. FastAPI выполняет синхронные эндпоинты в пуле
   потоков, так что сервер не блокируется. Перейти на async можно без изменения домена.
8. **Как удаляются просроченные данные?**
   Фоновая задача раз в 30 минут удаляет сессии с истёкшим `expires_at` вместе со всеми ответами.
9. **Как будете масштабировать?**
   Несколько экземпляров backend за nginx и пул соединений к PostgreSQL. Сервис stateless.
10. **Почему в core ходит бэкенд, а не браузер?**
    Запросу нужен сервисный токен команды. В браузере его увидел бы любой пользователь,
    поэтому он хранится в переменной окружения на сервере. Браузер передаёт только
    пользовательский JWT, а сервер один раз меняет его на профиль и выдаёт свою сессию.
