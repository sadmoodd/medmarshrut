## Что сделано

### Схема данных (PostgreSQL 16)

Четыре таблицы (подробно — `docs/Схема_данных.md`, диаграмма `docs/data_schema.png`):

| Таблица | Назначение | Связь |
|---|---|---|
| `patient_sessions` | Анонимная сессия: статус, канал, хеш токена, срок жизни | — |
| `session_answers` | Ответы по порядку, содержимое зашифровано | N к 1 сессии |
| `triage_results` | Итоговая рекомендация, обоснование зашифровано | 0..1 к 1 сессии |
| `emergency_events` | Журнал выявленных экстренных признаков | N к 1 сессии |

Ограничения целостности: внешние ключи с `ON DELETE CASCADE` (удаляешь сессию — удаляется
всё), уникальность `(session_id, step_id)`, CHECK-ограничения для статуса, канала, срочности
и места обращения, индексы по `expires_at`, `status`, `urgency`, `red_flag_code`.

Модели описаны в `backend/app/models.py` (SQLAlchemy 2.0). Таблицы создаются при старте приложения.

### Защита персональных данных (ФЗ-152, GDPR)

| Мера | Реализация | Файл |
|---|---|---|
| Минимизация сбора | Нет ФИО, телефона, адреса, полиса, точного возраста, названий лекарств | `knowledge.py` |
| Очистка свободного текста | Телефоны, e-mail, номера из 6+ цифр заменяются на «[скрыто]» до сохранения | `text_analysis.py: scrub_pii` |
| Шифрование при хранении | Ответы и обоснование — Fernet (AES-128-CBC + HMAC-SHA256), ключ в переменной окружения | `security.py: EncryptedJSON` |
| Минимизация профиля MAX | Core отдаёт СНИЛС, ОМС, ФИО, телефон, дату рождения — сохраняем только возрастную группу и пол (зашифрованы), имя лишь показываем в приветствии | `max_gateway.py`, `models.py: profile` |
| Сервисный токен core | Только в `.env` на сервере, не в git и не во фронтенде; токен пользователя стирается из адресной строки | `config.py`, `maxBridge.js` |
| Псевдонимизация | ID пользователя MAX хранится только как HMAC-SHA256 с секретной солью | `security.py: pseudonymize` |
| Контроль доступа | Случайный токен 256 бит на сессию, в БД только SHA-256, сравнение за постоянное время | `security.py` |
| Ограничение срока хранения | TTL 24 часа, фоновое удаление каждые 30 минут | `services.py: purge_expired` |
| Право на удаление | `DELETE /sessions/{id}` и кнопка «Удалить мои ответы» | `api.py` |
| Защита инфраструктуры | Порт БД не публикуется, backend не от root, `Cache-Control: no-store`, CSP в nginx | `docker-compose.yml`, `nginx.conf` |
| Секреты вне кода | Ключи в `.env`; compose не запустится без `DATA_ENCRYPTION_KEY` и `HASH_SALT` | `.env.example` |

Шифрование сделано на уровне приложения через тип `EncryptedJSON`: код работает с обычным
словарём, а в БД попадают только зашифрованные байты. Даже администратор БД или украденный
дамп не раскроют жалобы пациентов без ключа. Тест `test_answers_are_encrypted_at_rest`
проверяет, что слово из ответа не встречается в БД в открытом виде.

Открыто хранятся только обезличенные поля (статус, срочность, специальность) — для
статистики, например «сколько экстренных случаев за день».

## Текст для защиты (1 минута)

«Я отвечал за данные и безопасность. Главный принцип — не собирать лишнего: мы не
спрашиваем имя, телефон и адрес, а возраст — только группой. Если пользователь всё-таки
напишет телефон в свободном поле, он будет вырезан до сохранения. Медицинские ответы
хранятся в базе зашифрованными, поэтому утечка дампа ничего не раскроет. Сессия живёт
24 часа и удаляется автоматически, а пользователь может удалить свои данные в любой момент
одной кнопкой. Схема из четырёх таблиц с каскадным удалением и CHECK-ограничениями
обеспечивает целостность данных.»

## Вопросы комиссии

1. **Как вы соблюдаете ФЗ-152?**
   Минимизируем сбор (нет идентифицирующих данных), шифруем медицинские данные, ограничиваем
   срок хранения 24 часами, даём право на удаление, ограничиваем доступ токеном. Для
   реального запуска нужны согласие на обработку, политика конфиденциальности и уведомление
   Роскомнадзора; инфраструктура должна быть в РФ.
2. **Являются ли собранные данные персональными?**
   Сведения о здоровье — специальная категория. Но без идентификаторов (имя, телефон, точный
   возраст) связать их с человеком нельзя. ID из мессенджера хранится только как HMAC.
3. **Почему шифрование в приложении, а не средствами БД?**
   Тогда ключ и данные разделены: администратор БД или украденная резервная копия не
   раскроют содержимое. Шифрование диска защищает только от кражи носителя.
4. **Где хранится ключ шифрования и что будет при его утечке?**
   В переменной окружения (`.env`), не в коде и не в БД. При утечке ключ меняется; так как
   данные живут не дольше 24 часов, перешифровывать почти нечего.
5. **Почему в БД хранится хеш токена, а не сам токен?**
   Утечка БД не даст доступа к чужим сессиям: по хешу нельзя восстановить токен.
6. **Почему справочники вопросов не в БД?**
   Они меняются вместе с логикой, их нужно ревьюить и тестировать как код, поэтому они в git
   с номером версии. Версия записывается в каждую сессию (`kb_version`).
7. **Зачем таблица emergency_events?**
   Это аудит безопасности: какие экстренные признаки найдены и на каком шаге. Помогает
   разбирать случаи и улучшать правила.
8. **Что произойдёт с данными при удалении сессии?**
   Каскадно удаляются ответы, рекомендация и журнал событий. Тест проверяет, что в таблице
   ответов ничего не осталось.
9. **Как защищена база от доступа извне?**
   Порт PostgreSQL не публикуется наружу, доступ есть только у backend внутри сети Docker.
   Пароль задаётся через `.env`.
10. **Core присылает СНИЛС и ФИО. Где они хранятся?**
    Нигде. Клиент core сразу выбирает из ответа `_id`, дату рождения, пол и имя. Дата
    превращается в возрастную группу, `_id` — в HMAC, имя уходит только в приветствие.
    Тест `test_profile_pii_is_not_stored` проверяет, что СНИЛС, полиса, телефона, имени и
    даты рождения нет в БД.
11. **Как защищаетесь от SQL-инъекций?**
    Все запросы идут через ORM SQLAlchemy с параметрами; строки в SQL не склеиваются.
    Входные данные дополнительно проверяет Pydantic.
